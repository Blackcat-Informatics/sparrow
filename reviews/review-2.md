Verified by reading the source:

1. **Open, fence, seed.** `Store::open` (`storage.rs:1426`) now calls only `migration::fence`. Both writer-format lifts and both checkpoint seeds go into one `WriteBatch`, which `catalog_upgrade::commit` writes with sync. Both checkpoints are then validated; a missing one returns `STORAGE_FAILURE` (tested for `owner-graph-index-upgrade`). The lifts are the same `enable_event_fallback` and `enable_owner_graphs` functions; `writer_format.rs` is untouched, so no family is renumbered. A store with no `rdf:graph:record:` key or no `rdf:g:` key seeds that migration complete. The core test shows that a new store reports both migrations complete after an ingest. The open runs no page.
2. **Pages.** `Writer::migration_page` commits through `Writer::commit`, which calls `durability::apply`. That path checks the durability latch and `space.check()`, admits the data write under the same `owned_rdf_metadata` condition `artifact_rdf::admit` used, latches a failed write, and writes with sync. Rows and checkpoint go in one batch. `catalog_upgrade::step` now calls `page`, so `run`, `step` and the online fallback page all share one page builder. `owner_graph_page` is the old `owner_graph_step` body without its commit. The old loops (`event_fallback_rdf::upgrade`, `upgrade_owner_graphs`, `owner_graph_step`) are removed. `RdfWrite` reads `rdf:next` and the term counters from the DB when it is built, and the writer does not cache them, so running pages online cannot collide identities with ingest; the writer lock serializes both. When page staging fails, nothing is committed, the checkpoint stays put, the per-migration `failure` is latched, and the worker retries on the 60 s tick. A failed write latches durability, and the worker then ends the daemon.
3. **Readers.** `migration_state` reads both checkpoints from the view's own snapshot, which is taken under the writer lock during capture. The only two places that set `scoped` (`rdf_view.rs:1011`, `scope.rs:358`) are gated on `owner_index`. `fallback_pending` compares graph keys in the same order the job iterates them and reads the manifest from the snapshot. The whole-live-store capture also goes through `include_record`, so it counts pending graphs too. Correlation clears `fallback`. `index_coverage_complete` adds `event_fallback_pending == 0`. Strict reads refuse with `INDEX_NOT_READY` (tested). Ingest during the migration writes `rdf:o:` rows and fallback facts in the same batch (tested). A late narrow scope gives equal row sets before and after the index completes (tested).
4. **Query-only.** `Store::open` has no query-only branch, so a query-only open applies the fence batch, as `docs/interfaces.md` already says of open-time upgrades ("any open, query-only included"). `main.rs:199` starts no maintenance worker in query-only mode, and `migrate_step` has no other caller, so a query-only daemon cannot write a page. None of verify-backup's checks reads a key the fence writes: store id, `pressure.phase`, `durability.failure`, `unique_payload_chunks` (`ref:`), the records window, artifact bytes and the closed line. It only prints `store_format`. The extended query-only RPC test passes with both migrations pending. I accept the fence write on query-only opens: it is smaller than the full backfill the eedb484 query-only open already ran.

The schema stays 69 by a reversible decision, recorded in `implementation.md` Decision 1 and in `docs/interfaces.md` ("The wire schema stays 69 ..."). I found no written rule that a field addition must advance an undeployed schema; the convention is one advance per shipped feature, and live is on 68 by the 06:05 ruling. Agreed. The client crate does not decode `Status`, and MCP declares no output schemas, so no other consumer needs updating.

The acceptance measurement has not been run.** Issue acceptance 1 and the plan's Acceptance both require it: on a copy of the nightly under unit-like limits, `status` answers within 10 minutes, the backfills finish in the background, and status shows progress. `implementation.md` lists it as not done. This needs no code change, but `deploy/verify-backup.sh` cannot supply it alone. That script runs `--query-only`, which by design never runs a page, so it can show "serves at once" but not "finishes in the background". Run a writable (non-query-only) daemon on a reflink copy under `CPUQuota=100%`, `IOWeight=20`, `MemoryHigh=2G`, outside 07:45 to 08:00 per the 06:35 ruling. Record time to first `status`, total backfill time, the journal progress lines, and the per-page writer hold that the report names as the remaining online cost. Then free the copy.

**R2. A new duplicate helper, against AGENTS.md "Give each local helper one implementation".** `event_fallback_rdf::counts` (`event_fallback_rdf.rs:86`) and `rdf_index::owner_graph_counts` (`rdf_index.rs:358`) have the same body: walk a prefix, count every key, and count those at or before a frontier key. Both also overlap `Writer::count_prefix` (`storage.rs:1136`). Use one helper, for example a prefix count bounded by an optional frontier, called by both and by `count_prefix`. In the same new `fence` path, `rdf_index::any_key` is introduced while `catalog_upgrade::seed`, called from the same function (`event_fallback_rdf::fence`), keeps its own inline copy of the same "first key under prefix" check (`catalog_upgrade.rs:132`). Route `seed` through `any_key`. `make census-check` runs inside `make check` and may also flag the new pair.

**R3. Two behaviors the issue names have no execution evidence at any entry point.**
- (a) Status `failure`: "status reports ... failure", and per the focus, failure is latched, retried and never skipped. No test runs `migrate_step` on a failing page, so neither the latch in `Store::migrations()[i].failure`, the unchanged watermark, nor the clearing on the next successful page has ever executed. The existing `event_fallback_rdf` unit test covers only `catalog_upgrade::run`. Add to the core migration test: corrupt one record graph beyond the frontier (as the unit test does with `rdf:graph:record:f`), call `migrate_step` and expect `Err`, check that `failure` is `Some` and `done` and `watermark` are unchanged, restore the graph, then check that the next step clears `failure`.
- (b) The SPARQL pending signal on the wire: "SPARQL answers over unmigrated metadata graphs report that the event-fallback migration is pending". The core coverage count is tested. Nothing executes `index_coverage_complete` (no test anywhere calls it), `set_event_fallback_pending` in `rpc/sparql.rs`, or the agent's `coverage.event_fallback_pending` rendering. The extended query-only RPC test already serves a pending copy. Add one CLI `sparql` call there that asserts `coverage.event_fallback_pending` is non-zero and `coverage.complete` is false.
