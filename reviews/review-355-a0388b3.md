## Evidence assessment

- Cause. `rpc.rs:4497` is the second `.unwrap()` on `running`, the oneshot receiver whose
  sender `entered` lives in the query closure. `RecvError` means the closure was dropped
  without running. That happens when `lookup` fails at `admission.reader()?` before `run`.
  `Admission::new(Semaphore::new(1))` gives `writer_reserve(1) == 0`, so exactly one reader
  slot. The read's `Admitted` drops on the blocking thread at the end of the `run` closure.
  With the old field order, `_operation` was released first. That release hands the permit to
  the test's `acquire_owned()` waiter and wakes it, while `_reader` is still held. The test
  task can then run `drop(permit)`, check status, and start the next `query_work`, whose
  `reader()` meets the held slot and refuses `RESOURCE_LIMIT`. The closure is dropped, and with
  it `entered`. The race is real and matches the observed error.
- Fix. Rust drops struct fields in declaration order. With `_reader` declared first, the
  reader slot is free before the operation permit is handed on, so a caller woken by that
  permit finds both free. Every `Admitted` is built with named fields, so nothing else
  changes. Writers take no reader slot, so their behaviour is unchanged. A reader that arrives
  concurrently during the two releases can still be refused in either order, but that is the
  existing non-waiting reader contract, not this defect. The fix is correct and minimal.
- New test. It drives the real `Admission::reader()`, the real `Admitted` drop and the real
  tokio semaphore. It polls one waiter for the operation permit with a waker that records the
  free reader slots at wake time, then drops the read. tokio wakes the waiter inline inside the
  release (confirmed in `add_permits_locked`), so the recorded value is fixed by the drop order
  alone. The value is 2 with the new order and 1 with the old one, with no threads, sleeps or
  timing, so the test is deterministic. Its name and doc comment state the invariant and the
  issue. It would fail on the old order, which makes it a real regression test.
- Hook: `commit349b.log` shows the tree (`.worktrees/349-...`), parent `ee79931`, the commit
  `a0388b3`, and `EXIT=0`. The new test (line 923) and the flaky test (line 989) ran and passed.
- PR body: its claims match the code and the log. It says the causal link is inferred and the
  load failure was not reproduced. It says the old-order failure of the new test was reasoned
  from the code and not rerun, which matches my reading of the tokio release path.
